# Theme Spec — four themes, light and dark

Tiffin ships four themes. Each has a light and a dark variant, so eight
palettes in total. A device picks its own; a host admin can push one to every
device (see §6).

Source of truth is `lib/ui/theme/`. This document explains the intent so it
doesn't get relitigated.

## 1. The themes

| Theme | Identity | Shape and depth |
|---|---|---|
| **Neobrutal** *(default)* | Tiffin's own look, now carrying colour | 3px ink border, hard 4px offset shadow, radius 0, mono type |
| **Clean** | Flat and quiet, for a long admin shift | hairline border, one soft shadow, radius 8 |
| **Frost** | Frosted glass on chrome only | translucent sheets over solid content, radius 16 |
| **Clay** | Soft, round and warm | radius 28, inner highlight, large soft shadow |

Neobrutal stays the default: it is the app's identity, and a fresh install
should look like Tiffin rather than like anything else.

## 2. Tokens, not colours

Screens never name a colour, a border width or a duration. They read
`context.tokens` and name a *role*:

```dart
final t = context.tokens;
t.color.ink        t.text.body       t.shape.borderBase     t.motion.fast
```

These were compile-time constants until the app needed more than one look.
Spacing (`NbSpace`) and intensity (`NbIntensity`) deliberately stayed constant —
an 8pt rhythm is not a matter of taste, and keeping it static halved the
migration.

A screen picks an **intensity**, and the theme decides what that means:

| Level | Where |
|---|---|
| `NbIntensity.full` | Scan accept/reject; primary CTAs (submit top-up, confirm reversal) |
| `NbIntensity.restrained` | Admin data surfaces — member tables, calendar, settings forms |

## 3. Palettes are authored in OKLCH

`lib/ui/theme/oklch.dart` is a small pure-Dart OKLCH → sRGB converter. Equal
steps in OKLCH lightness are equal *perceived* steps at every hue, so a tonal
ramp can be generated by holding hue and chroma and stepping lightness. HSL does
not have that property, which is why hand-tuned ramps rarely look coherent side
by side.

This is what makes eight palettes tractable: **dark mode is the same hue and
chroma at inverted lightness**, not a second hand-picked set. Dark accents also
drop a little chroma — a value that reads as vivid on white glares on near-black.

Text drawn on a variable fill is **derived**, not hand-paired:
`palette.on(fill)` picks whichever of ink/surface/background reads best. A fill
can be retuned without silently dropping its label below AA.

## 4. Colour carries category, never state

The admin dashboard is colour-coded by domain — members, money, kitchen,
system (`NbTone`). That is *category* only. Every tile still carries its own
icon and label, so nothing is lost by not seeing colour.

State is never colour alone. Accept/reject and grace/pending always carry, in
addition to colour: a distinct **icon**, a distinct **border weight**, and a
**text label**.

## 5. The contrast test is the guardrail

`test/theme_contrast_test.dart` asserts WCAG AA across all eight palettes:
4.5:1 for body text, 3:1 for large text and meaningful boundaries. It found
eleven real problems when the themes were written — mid-lightness accents that
cleared neither white nor black text, and hairline borders that left a card
indistinguishable from the page. Those were fixed, not excused.

One nuance it encodes: WCAG 1.4.11 asks that a *component* be distinguishable
from what is next to it, not that any single token carry that alone. A card
passes if **either** its border or its fill separates it from the page — which
is how Neobrutal can use a pastel tile behind a 3px ink border while Clean has
to earn it with the border.

`test/theme_render_test.dart` renders every shared primitive under all eight
variants, including at the 320px reflow floor.

## 6. Where the setting lives

**Settings ▸ Appearance**, reachable from every role via the app bar overflow.
Theme · light/dark/system · animations.

Each device keeps its own choice in `SharedPreferences`. A host admin can push
one look to every device; enforced devices show *why* their controls are
read-only rather than silently ignoring taps.

The policy travels on the pre-login endpoint, so a client renders the enforced
theme on the login screen instead of snapping to it after sign-in.

## 7. Motion

Motion is part of a theme's personality, not a shared constant: Neobrutal
snaps, Clean is understated, Frost glides, Clay overshoots. Everything routes
through `lib/ui/shared_widgets/motion.dart`, so "animations off" is one branch.

Three things can switch it off and **any one of them wins**: the device's
Appearance setting, a host policy, and the phone's own reduce-motion
accessibility preference. The last belongs to the viewer and is read at use
time, never overridden.

The camera preview stays still — it is live video under a performance budget,
so the scan screen gets the verdict overlay and nothing else.

## 8. Translucency (Frost only)

Frost is the one theme that is translucent, and only on **chrome**: sheets and
overlays, never content. A semi-opaque plate sits *behind* the blur, because
blur softens a backdrop without bounding it — glass alone has no guaranteed
contrast. Blur is capped at 14 so it stays cheap on a mid-range GPU, and it
collapses to a solid surface under reduced-transparency or high-contrast.

## 9. Accessibility invariants (apply to every theme)

- Touch targets ≥ 48px (`NbButton` enforces `minHeight: 48`).
- Focus is a colour **and** a weight change, so it survives with colour
  stripped.
- Body text ≥ 16px; form inputs never below 16px.
- Semantic widgets, labelled fields, `Semantics(button: true)` on tap targets
  that aren't real buttons.
- Dark mode never uses pure black on pure white — that combination causes
  halation and is fatiguing.

## 10. The logo

Drawn from tokens (`lib/ui/shared_widgets/app_logo.dart`), not loaded from a
PNG: a coupon stub whose border weight, radius and shadow come from the active
theme. Hard-edged under Neobrutal, puffy under Clay, with no artwork to keep in
sync and no resolution ceiling.
